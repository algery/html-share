## 容量与零正文回源的计量边界

- N13：10 个小型 HTML/CSS 项目并发发布，处理 P95 **238.55ms**，最大完整发布 **352.26ms**；20 个独立密码页状态同一出口首次校验，20/20成功，批次 **389.37ms**。100 个同时请求使用**同一个有效项目 grant**，P95 **155.65ms**，额外密码哈希 **0**。它证明并发请求能力，不证明100个独立身份或持续高吞吐。
- N13 哈希压力：直接并行35次 `crypto.generate()`，2活跃+32排队，34接纳/1拒绝，同时100读取 P95 **91.32ms**；RSS 增量 **28.89MiB**，事件循环最大延迟 **16.06ms**。RSS 从已经完成发布/校验预热的同一个 Node 进程开始，10ms采样；服务、Worker harness 与驱动共享进程。不是冷启动峰值、容器整体RSS或35个HTTP密码提交压力。
- K13 `correct`：20 VU各首次授权并读取，20次密码校验；正文请求 P95 **7.75ms**。`read`：100 VU各读一次，共用一个grant，HTTP duration P95 **124.99ms**、waiting P95 **124.94ms**、新增密码校验0。不能把 correct 阶段包含密码POST的总体耗时当静态TTFB。
- K13 `wrong`：新阶段独立配额，40次错误密码中30次进入校验、10次429，全部无grant；N13在已消耗20次校验配额后观察到10次401/30次429，两组计数前提不同。均检查Retry-After，且错误密码限流后钉钉入口仍200。
- K13 `upload`：10 VU各上传小型HTML/CSS，10次完成、10个新密码实开内容；`upload_processing_e2e_ms` P95 **1541.35ms** 包含1.5秒客户端轮询间隔，不是纯Worker执行耗时。每个HTML为43字节，容量限制另由边界测试覆盖；此结果不能替代正常企业网络下最大项目的60秒验收。
- N13在内容读取前截取发布计数，Server/Worker GetObject和正文bytes均0。K13最终计数含合法内容读取，Server分别为 correct **20次/5240bytes**、read **100次/26200bytes**、wrong **0**、upload **10次/430bytes**，精确等于授权内容读取；Worker四阶段均0。不能将包含内容网关的Server总GET错误要求为0，也不能把 `content` 独立计数器0解释成没发生内容读取。
- 所有容量结果来自本地Node24、隔离PostgreSQL/MinIO及回环/宿主网络；k6的MCP延迟标签不等于项目、Token和删除等管理API的完整P95验收。它们不证明生产硬件、跨地域OSS、长期可用性99.5%或持续速率。限流为单实例有界Map，多实例共享限流尚需部署方案与复验。
